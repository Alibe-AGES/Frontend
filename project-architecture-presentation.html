Project Layers Overview

Application structure

src/ ├── app/ │ ├── _layout.tsx │ ├── index.tsx │ └── __tests__/ ├── screens/ ├── components/ ├── hooks/ ├── server/ ├── utils/ ├── theme.ts ├── constants.ts ├── global.css └── ...

Responsibility split

  • src/app: route files and navigation boundary
  • src/screens: page-level composition and screen state
  • src/components: reusable UI atoms and controls
  • src/hooks: reusable stateful behavior
  • src/server: typed API client and request error handling
  • src/theme.ts: shared token definitions

Startup Flow Runtime

How the app boots

Entry point

package.json { "main": "expo-router/entry" }

Expo Router becomes the application bootstrap point.

Runtime path

Expo launch → App entry → src/app/_layout.tsx → Stack navigator → src/app/index.tsx → React Native rendering

Each route file in the app folder becomes a navigable screen.

Route and Screen Pattern UI flow

Keep routes thin

// src/app/index.tsx import { HomeScreen } from '@/screens/HomeScreen'; export default HomeScreen;

Good pattern

  • Route file only imports the screen.
  • Screen handles page composition and state.
  • Component library holds reusable UI pieces.

Bad pattern

  • Large layouts inside route files.
  • Business logic and UI markup mixed together.
  • Repeated markup copied across screens.

NativeWind + Metro Styling

How styling is wired

Key config

babel.config.js → jsxImportSource: 'nativewind' → nativewind/babel metro.config.ts → withNativeWind(config, { input: './src/global.css' }) src/global.css → Tailwind base + utilities

Usage

<View className="flex-1 bg-white px-6 py-8"> <Text className="text-2xl font-bold text-black"> Profile </Text> </View>

Static styling should use `className`; dynamic native styling stays in `style`.

Contributor Model Workflow

How contributors work

  • Clone repository and install dependencies.
  • Create a feature branch from develop.
  • Build UI in src/app, src/screens, and src/components.
  • Run TypeScript, lint, and focused tests.
  • Open a PR targeting develop.

Branching flow

git switch develop git pull --ff-only origin develop git switch -c feature/my-change # develop UI work # validate git push -u origin feature/my-change # open pull request to develop

This keeps feature work isolated and easy to review.
